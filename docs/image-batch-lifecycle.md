# 图片批处理的停止、恢复与资源清理

2026-10-27 完成第三阶段首批优化，范围为 `/image-compressor` 和 `/image-converter`。保留原路径、风格、格式、质量范围、下载与结果继续处理；仍逐张执行，不新增依赖、全局队列、后台任务或持久化存储，不复制 ToolKnit 代码。

## 已证实的问题

| 文件 | 原有影响 | 修改与理由 |
| --- | --- | --- |
| `app/components/image-compressor.tsx` | 编码等待期间离开页面，循环仍继续处理余下图片并创建结果 URL；卸载清理已结束，新 URL 无人回收 | 同步任务锁与取消信号；卸载取消，提交前检查取消，不再启动后续项。当前原生任务先完成自身清理，再结束批次 |
| `app/components/image-converter.tsx` | 导入解码未纳入取消；清空后旧文件可能回填，未登记的预览 URL 不能由项目列表清理；重叠导入按相同旧列表做去重 / 名额计算 | 导入独占锁、可取消 Image 加载、临时 URL 所有权集合，按当前同步列表计算预算；清空立即取消，旧任务按自身 URL 清理，不能清除新批次 |
| 两个组件的 `FileDropZone` 入口 | 文件尚在读头预检、还没调用父级导入函数时清空，旧上传回调仍可追加文件 | 清空递增上传版本并重挂载控件；回调闭包再比较同步版本，连 React 尚未提交清空时的旧回调也失效。不修改共用上传控件或其他工具 |
| 两组件的批次启动与列表更新 | 单靠状态中的 busy 值不能阻止同一事件轮次、渲染之前的两次启动；引用只在 effect 同步也会滞后 | 先设置同步任务 ref，再启动；列表 ref 与状态同时更新。对象 URL 创建 / 回收不再放进 React 可能重复调用的状态 updater |
| 两组件的绘制函数 | 压缩只关闭 bitmap，转换没有绘制资源的 finally，缺少确定性的画布收尾 | 在成功、失败、取消和同步异常路径均清零画布；压缩保留 bitmap.close，转换解绑 Image 事件并清空其源。不能据此认定原先永久泄漏或声称特定内存下降幅度 |
| 转换器的参数更新 | 参数 effect 在渲染提交后再清除旧结果，新增同步列表引用后还会触发额外渲染与 hooks 检查错误 | 改为实际参数变化的事件中清除旧输出，重复选择同值保留结果；运行时有同步锁，不允许改动正在使用的参数 |

## 调度与交互

`app/lib/serial-batch.ts` 只负责顺序、取消检查与逐项成功 / 失败回调，不持有画布、URL 或结果数组。输入批次取快照，最多一个处理函数在运行；单张失败继续下一张，取消和提交回调异常则终止。不增加并发数，避免未经实测扩大大图的同时解码数量。

原开始按钮运行时改为“停止处理”，沿用现有按钮样式与两列操作布局。停止后显示“正在停止…”，待当前原生操作收尾才解除运行锁。已成功的结果保留，可继续下载或交给后续工具；当前未完成项回到等待，再开始只处理非完成项，包括此前失败项。更改质量、格式或背景后，按原语义清除旧结果再重新处理。

转换器导入期间上传控件禁用，防止批次重叠；清空仍可用，并能立即开始新的导入。只有旧导入拥有的 URL 会在旧任务结束时清理。压缩的结果接收入口改用同步列表做整体校验，实际未接收时返回 false，不误确认成功。

## 仍然存在的边界

- `createImageBitmap` 和 `canvas.toBlob` 没有可强制终止的取消接口。停止会拒绝后续提交和任务，但要等待当前原生调用返回；不能承诺即时释放内存，永久不返回的原生调用仍会占用运行锁。大幅同步像素循环也只能在主线程让出后响应用户点击。
- ZIP 打包和转换器“下载全部”的原有延时下载循环不属于这个执行器，本轮没有加入它们的取消能力；不是全站所有批处理已统一。
- 真实图片验证使用 Node Canvas / Sharp，不是真实浏览器。适配器记录组件写入宽高 0，并将原生 backing 缩到 1×1；这不能代表浏览器内存峰值、解码兼容性、页面帧率或首屏速度。没有提供这些指标的前后对比。
- 已保存的浏览器访问限制未绕过，真实桌面 / 手机视觉与触控尚未验收；既有分包体积、vinext 路由分类及字体提示不隐藏。
- 未部署、提交、推送或修改 Release；版本仍为 1.1.0，MIT 和 Cloudflare 部署方式保持不变。
